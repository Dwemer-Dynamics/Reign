# Conversation prompt composition, layout 12

## Lossless conversation roles (2026-10-10)

Individual, party/Home and social-event writers now separate reference context, chronological history and the latest player contribution. Complete standing rules and drinking rules use system messages. Character data and live scene/state/memory are explicitly labeled reference messages. Each selected historical player turn uses a user message; only the responding NPC's earlier visible replies use assistant messages. Other witnessed characters and narrators use labeled reference messages, with stable opaque actor keys where an identity is not public. Role assignment uses observer-projected stored rows, never headings or names parsed from player text. Consecutive turns and identical bodies with distinct source identities remain distinct.

The latest player contribution is the final user message, with its original observer-permitted narration, actions, formatting and speech. Engine state, drinking state, cultural guidance and output instructions precede the conversation. Historical visible prose is explicitly not a JSON output example, new instruction, native action or consent receipt; the full current response schema remains authoritative. Existing narrative/audience projection and action authorities are unchanged.

This build introduces no content reduction, memory-window reduction, deduplication, new relevance selection or new provider/repair calls. Existing allocation and visibility policies remain in force. All previously selected context, repeated memory/continuity references, rules and original canonical transcript content are retained. Template slots are located before value substitution, including custom templates; substituted player text is never expanded again as template syntax. Missing custom latest-input slots cannot hide the final player turn. Legacy history that cannot be mapped exactly stays verbatim as an explicitly attributed reference, with `referenceHistoryRecords` reporting this coverage limit.

`conversationMessageStructure` records source/body hashes, structured/reference counts and no-reduction/no-additional-call facts. A server-only receipt binds the actual ordered role/content messages. Whole-exchange evidence is reconstructed across message boundaries only when the actual messages match that receipt. Assembly and final provider preflight reject missing/reordered history, changed roles, omitted actions or altered context even if a duplicate memory still contains the original words. Trusted server request clones retain that existing receipt; serialized or client-provided diagnostics cannot create one. Template boundaries use opaque markers that survive identity masking and never reach the request or its cache/budget hashes. The existing exact private-reasoning policy and appended repair instructions remain compatible. `liveTurnHash`/`liveTurnChars` cover the structured live message sequence; additive sizes remain in `messageSizes`.

Run artifact-bound `prompt_efficiency` after manifest-selected validation. Its `message_structure_*` contracts cover both attribution examples, verbatim actions and literal template-like text, chronology, third parties, identity/privacy projection, custom templates, full evidence/recall delivery, final JSON serialization and tampering rejection. Existing production noble/commoner dialogue/party/event fixtures assert real assistant history and unchanged rules/schema/context. Offline proof establishes delivery and role structure; live model attribution quality still requires separately authorized provider/native acceptance.

2026-09-08. Character accuracy and attribution take precedence over token savings. This change covers the production dialogue/event envelopes used by individual, Homes/castle, party/social and office conversations, plus correspondence and the hidden action planner. ## Standing rules and applicability

Layout 11 (2026-10-08) places the complete structured-action rules and catalog at the front of dialogue/event requests. All conversation-eligible action IDs, labels, movement flags, parameter keys/types/required flags and choices remain present; identical parameter definitions are stored once and actions reference zero-based parameter indexes. The main JSON example now always includes the full neutral `structuredActionDecision` on structured routes and disables the covered legacy action gate. Legacy routes retain their existing gate. Missing/malformed model output still uses bounded fail-closed recovery; prompt changes do not guarantee that a provider will never need repair.

Fixed common rules precede conditional noble, room and office sections. The independently budgeted drinking packet inserts only fixed rules before character data and appends current physical state to the live suffix; core history is allocated first and retained intact. Its budget includes both portions, while aggregate preflight still measures the final messages. `drinkPromptBudget` retains core accounting and adds separate `rulesHash`/`stateHash`; `contentHash` binds both portions. The final live hash/size includes drink state.

Life-event relevance still selects the same records, then renders them chronologically with source-ID tie breaking. Native history interpretation is stated once. Recent summary provenance and partial-view instructions are likewise stated once, attached to one protected summary so allocation cannot discard the policy separately. Each summary keeps its source identity, timestamps, compaction state and coverage metadata; the 30-message/30-summary windows and original storage remain unchanged. These are per-call text/layout changes; provider cache hits, billed tokens and end-to-end latency require later measurement.

`PromptRuleComposition.cs` composes explicitly named requirements. A layer that needs a shared rule declares that dependency even when another layer also requires it. The rule renders once in a request. Missing rules, conflicting definitions, empty required templates and cycles fail before provider submission. Different observers, subjects, permissions, duties and exceptions retain separate content. This is not an automatic semantic deduplicator: overlapping prose in distinct character-type templates stays intact until an equivalence review and behavioral evidence justify extraction.

World tone, noble danger/formality, memory, identity, action receipt, scene-state and output contracts retain their wording. Noble rules are omitted only for explicitly false native `isLord`. A native encountered-resident commoner classification also proves non-noble applicability. Otherwise missing/invalid status retains conditional noble guidance with an explicit prohibition on inferring a title or office. Office rules come from the existing native posting/office resolver, and appear after the reusable policies. Room attire uses the existing native scene selector. The original commoner role and household rules remain in every applicable character foundation, including letters. No model-selected or player-keyword-only omission is introduced.

Correspondence and the planner compose their own contracts; they do not inherit a dialogue output schema. The standing rebellion decision contract in letters moves out of the live suffix into the system prefix, with unchanged wording. Live decision evidence stays in the suffix.

Every provider request remains self-contained. Standing rules cannot safely be sent once per conversation and then omitted from independent chat-completion requests. Stable prefixes permit the provider's existing implicit cache to reuse work. No new provider flags, model route, subscription change or unsupported claim of cached-token savings is introduced. Missing provider cache usage remains unreported.

## Wealth evidence

Native wealth v3 computes personal wealth from `Hero.Gold` alone. Party cargo has an explicit `observed`, `unknown` or `not_applicable` state and a nullable value. Clan funds remain distinct, including the existing warning when Bannerlord exposes the same wallet. `visibleWealthTier` is deprecated and emitted as unknown; visible presentation comes from the separate appearance and actual scene-attire evidence.

Prompt projection leaves historical storage untouched, discards the misleading cargo-derived visible label, recomputes historical personal tiers only from supplied known cash, and treats old zero cargo as ambiguous. Unknown economic capacity cannot become zero cash. Rich dress, low personal cash and strong clan backing can coexist. This does not infer public knowledge of a private treasury or convert equipment value into spendable gold.

## Complete player narrative (2026-10-09)

Ordinary player contributions preserve their complete narration, dialogue, formatting and order through current prompts, history, scene handoffs and recall. No keyword or semantic classification of inferred player thoughts may remove story text. NPC-authored private interpretations retain their separate observer rules. Explicit whispered words retain recipient restrictions; mixed narration keeps the surrounding physical action, and an unnamed whisper in a single-interlocutor chat reaches that interlocutor.

The source journal/receipt remains immutable. Scene interpretation is annotation only, never a visibility gate or a prerequisite for narrative acceptance. The writer responds naturally without mandatory per-gesture actionResponses/replyQuote evidence or related repair calls. Drinking, structured action decisions, explicit scene movement, party membership and real commitments keep their specific authorities. Narrated attempts are not native execution or blanket consent. Repairs preserve required actionGate metadata and report schema completeness separately from remaining continuity violations. Retrospective asked/said claims use original speaker ownership, including an NPC's own introduced question. Historical venue callbacks do not establish a current relocation.

Provider-free regression coverage is in the existing conversation input, observer, continuity and dialogue-claim suites. Captured empty provider responses still use bounded format recovery; this does not promise providers can never return empty output. Native acceptance and probabilistic response quality remain distinct from offline verification.
