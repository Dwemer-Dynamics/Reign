## Selecting and describing the moment

1. After the current exchange finishes, freeze campaign, timeline, conversation/session, player, latest completed exchange boundary, four exchange IDs, original turn IDs/hashes, per-turn visibility, physical presence and scene appearance. A new exchange may start after that snapshot without changing the pending View job.
2. Load the exact accepted source messages on the server. Apply the existing viewer/audience rules before constructing the prompt. A whisper visible to the player may inform that player's private View; it must not expose other recipients' private data, notify NPCs or become a public memory merely because an image was made.
3. Make one structured selection call through the active dialogue route. Ask for the most visually or emotionally significant enacted moment in that window, even if it is quiet. Choose one instant; do not combine the best action from one exchange with incompatible positions or props from another. The window includes subsequent corrections that may retract an earlier claim.
4. Require a versioned result with selected exchange/turn IDs, exact supporting excerpts, a short selection reason, involved stable character IDs and roles, who acts on whom, observable pose/contact/expression, factual setting, relevant objects/clothing and unknowns. Keep this internal evidence separate from the short player-facing caption. Unknowns may receive unobtrusive staging but cannot become new plot facts.
5. Validate IDs and exact quote substrings against the permitted source window, distinguish direct from reported/remembered/hypothetical action, and check participants against presence at the selected instant. Evidence checks establish provenance; they do not prove semantic correctness by themselves. Keep a source-labeled visual acceptance set for that judgment.
6. Build the image prompt deterministically from that result, identity mapping and a dedicated documentary-photo layer. Reject invalid structured output before an image request. Expose a clear failure/retry state without an automatic repair/re-generation loop.

The output must distinguish speech, figurative language, proposals, memories and enacted narrative. A metaphorical threat does not become physical violence; a proposal is not a completed embrace or journey. Illustration must not execute a game action, award consent, alter relationships or write imagined facts into NPC memory. An enacted roleplay gesture can be illustrated without changing native campaign state.

Use a third-person observational camera that can show the player when involved. Specify natural available light appropriate to the recorded setting, plausible lens perspective, real skin/cloth/metal, coherent anatomy and candid interaction. Avoid painterly/CGI/game-screenshot rendering, glamour retouching, posed catalog arrangements and invented dramatic props or events. Composition follows the action: **full-body reference inputs do not require every output to be a rigid full-body lineup**. Keep all involved identities recognizable and the important action visible.

## Resolution and provider adapter work

Add a tested capability contract keyed by provider, actual model and transport. It must describe reference support/count, size constraints or ratio/resolution buckets, maximum native output, quality controls, response format and provenance date. Catalog metadata is useful only where it actually supplies those fields; fill gaps from the provider's official schema and bounded acceptance evidence.

Current source needs changes before it can honor the requirement:

| Adapter | Current limitation | Required View behavior |
| --- | --- | --- |
| NanoGPT GPT image route | `MapToGptImageSize` maps every landscape request to 1536x1024 | Preserve the selected model's documented exact-size capability, not a universal legacy cap |
| AtlasCloud | Some branches hard-code 1k; Seedream V5 maps landscape to 2720x1530 | Pass model-specific 3:2 plus its verified maximum size/resolution controls |
| OpenRouter | Non-GPT landscape is mapped to 16:9 and resolution to 2K | Respect the exact selected model's ratio, maximum resolution and reference schema |
| Codex subscription | `CodexImageFraming` reduces sizes to generic prose and otherwise follows reference composition | Explicitly request 3:2 and maximum supported resolution; inspect actual output and report runtime-managed capability uncertainty rather than treating API limits as subscription guarantees |

Official documentation checked on 2026-10-29 establishes why one hard-coded maximum would be misleading:

- [OpenAI image generation](https://developers.openai.com/api/docs/guides/image-generation) documents a GPT Image 2 API limit of 8,294,400 pixels, 3840 maximum edge and 16-pixel alignment. Under those constraints, the computed largest exact 3:2 aligned rectangle is 3504x2336. This is an API sizing example, not proof the current Codex, NanoGPT or OpenRouter route exposes it. Its [API reference](https://developers.openai.com/api/reference/resources/images/methods/generate) treats resolutions above 2560x1440 as experimental.
- [Google's image generation tables](https://ai.google.dev/gemini-api/docs/image-generation) include a nominal 3:2 4K output of 5056x3392 for particular models. That is not mathematically exact 3:2, demonstrating that an advertised ratio label does not prove exact output geometry. It also does not establish the capability of a retained preview-model alias through a reseller.
- [xAI's image prompting guide](https://docs.x.ai/developers/model-capabilities/images/prompting-guide) documents 3:2, 2k and quality controls for its specified current image model. Validate the exact Atlas/OpenRouter model and transport independently.
- [NanoGPT support](https://nano-gpt.com/support) directs callers to the exact image-model catalog ID and supported inputs. Model-family similarity does not establish endpoint, size or subscription allowance compatibility. Atlas model pages could not be fetched by the documentation reader, so their exact maximums remain unverified.

Prefer exact native dimensions. For a documented nominal 3:2 bucket with small alignment rounding, retain the untouched provider output and permit only a recorded, deterministic edge trim of at most 1% of source pixels to the largest exact 3:2 rectangle. Keep the prompted action inside a safe margin and prove no important content is cut. This does not authorize repurposing 16:9/square art, stretching, padding or enlarging low-resolution output. A selected transport that cannot meet these bounds reports unsupported resolution before spending on an image. Do not switch models silently. Archive both original dimensions and final exact-ratio dimensions.

The highest-resolution choice remains the user requirement even when a model's upper range is slower or experimentally less reliable. Record that status with the capability evidence; do not silently lower quality or resolution. Respect existing content/profile eligibility and provider refusal paths. An unclear source is not permission to infer consent or route around a refusal.
