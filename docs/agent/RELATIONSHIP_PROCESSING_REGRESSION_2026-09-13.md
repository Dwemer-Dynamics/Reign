# Relationship processing regression: investigation and deployed fixes — 2026-09-13

The regression was caused by later features bypassing the original batching discipline around an otherwise functioning PostgreSQL bulk writer. The August 13 observer-specific Public Standing change introduced per-direction reads; native projection added a roster lookup per pair; fling processing parsed about 46 MB of personality documents despite cached judgments. Repeated lifecycle preparation and full roster reinsertion added further work and transaction contention. These concrete paths have now been repaired and deployed.

The **final deployed build averaged 4.516 seconds per relationship day**, range **4.180–5.197 seconds**, across four fresh native days with 1,593–1,616 pair evaluations each. The supplied retained days took 18–20 seconds. Relationship processing finished before the final native pause; the wider quiescence procedure still added about **104 seconds** beyond native advancement. The complete Release validation passed **195 relationship checks, 62 persistence checks, 555 MCP checks and 11 relationship-kernel checks**; the final focused correction passed all **195 relationship checks** again. Hygiene passed. This is a material throughput improvement, with unchanged tested simulation rules, but the original sub-second processing budget and a game day arriving every few seconds are not yet certified.

**Implemented and deployed.** Standing rows, parsed sources and relevant roster facts are scoped to one connection/processing context. Writes mark relevant facts stale while retaining participating IDs, so the next read refreshes the context in a batch. Nested projections invalidate their outer scope too; missing rows and changed player status remain accurate. Native player IDs are loaded once per valid context. Observer-specific Favoring, Charm/jealousy, spouse adjustments and NPC-to-player projection remain authoritative; mutable trait files are not replaced by a permanent cache. Fling preparation reads only eligible unresolved profiles, and batches every individual daily roll receipt with flushes before dependent spark/encounter work. Rare effects remain ordered. Indexed co-presence replaces repeated group scans. Lifecycle writes reuse command preparation while executing immediately. A fresh native heartbeat prioritizes the active campaign/timeline, with a maintenance opportunity every ninth selection and at most one standing-invalidation batch before offering a relationship day.

Full identity synchronization now uses the existing PostgreSQL roster batch writer after preserving departing implicit identity knowledge, inside the original replacement transaction. A sample during the first deployment's nine-second BEGIN wait showed the roster writer predominantly on individual inserts; source confirmed it deleted and reinserted all 4,305 NPCs one command at a time. This was an additional source of long transaction holds. The replacement is covered by an oracle comparing **all persisted columns for 128 diverse roster entries**, including family, roles, clamped values, Unicode names, timestamps and rollback. Activity samples establish occupancy, not exact CPU attribution or every blocking owner. Successful durable relationship days now emit bounded `relationships.day_completed` records with campaign/timeline/day, build identity, phases and read/profile/write counters. Independent lifecycle and fling timings are exposed. The standard relationship validation now explicitly includes the world-model standing, invalidation, co-presence and scheduler tests, as well as lifecycle immediate-read/rollback and fling receipt/profile contracts. No probability, eligible population, encounter cadence or history-retention rule was reduced to obtain these gains.

**Additional improvements can preserve quality, accuracy and immersion.** The guiding constraint is to perform the same simulation with less repeated work. Each recommendation below needs equivalence checks before deployment; none requires reducing the population, dropping elapsed days, changing social probabilities or weakening checkpoint safety.

| Improvement | Benefit and gameplay safeguards |
| --- | --- |
| Use a compact, typed simulation context alongside the full character documents. | Relationship calculations need a small subset of the narrative/trait data. Load only those fields for participating NPCs, while keeping complete profiles available for dialogue and other consumers. Preserve exact values, rounding, provenance and schema versions. This reduces transfer and JSON allocation without simplifying personalities or dialogue. |
| Cache immutable values and invalidate mutable values by revision. | Permanent MBTI and established fling judgment can follow their existing immutability rules; standing, charm, kingdom, spouse and other changing facts need explicit revision or event invalidation. Scope caches to campaign/timeline/Save Sync generation so a restored save cannot inherit later facts. This retains accurate reactions while eliminating repeated parsing and lookups. |
