# Launch packaging and paired-source proof

Use `reign_get_validation_plan` with `all` before changing repository ownership, shared compilation, validation infrastructure or installer behavior. Recheck `reign_get_validation_status`, pass the current task UUID to `reign_validate`, and retain the exact all/Tier 4 report, hygiene report, duration and source fingerprint. The unchanged OS build lease is authoritative across both checkouts.

When MCP transport does not target the restored checkout, the canonical fallback supports `-PlanOnly` and `-RequestingTaskId`. It bootstraps only ReignMcp and then calls the existing `--plan-cli` or `--validate-cli` engine. Use `-Restore` for the first fresh checkout. Keep package caches and temporary build files on the selected development drive. This is not an alternate product build path.

The paired local layout is `Reign` beside `ReignServer`. Run the public repository's `ReignRelease/Connect-Repositories.ps1` to establish the five declared source junctions in private Reign. Edit server-owned files in ReignServer and client-owned files in Reign. The junctions are ignored by private Git and contain no duplicate source. `reign.repositories.json` allows only the exact sibling checkout and directories. Missing, substituted or extra source links must not be used to broaden access or bypass ownership. Both repositories must pass enforced hygiene with the exact Dwemer-Dynamics origins; the validation fingerprint includes server-owned source and its policy.

`LaunchInstallationTests` checks installation records with spaces/non-ASCII paths, protocol/layout rejection, native PostgreSQL archive-tool selection, credential exclusion from command lines, and Windows argument round trips. `ReignSourceLayoutTests` checks repository-layout validation and the source boundary. These tests do not prove that a complete installer works.

Release packaging must allowlist validated runtime files, verify every external payload's size and SHA-256, and omit `verification_contracts`, campaigns, API credentials, logs, backups and game-owned binaries. Private Reign client source must never enter a public server export. Keep runtime, models and large content separately versioned so a server code update does not require another portrait download.

Official dependency archives are extracted as run-owned inputs; only the selected module's Steam `Win64_Shipping_Client` binaries and module assets enter the payload. Debug symbols and alternative Game Pass binaries remain excluded. Upstream notices are tracked without Git newline conversion and verified against their recorded hashes. Both repositories' Git attributes participate in the validation fingerprint because checkout byte transformations affect those inputs.

`reign_build_release_runtime` is the leased component build route; its CLI fallback is `reign-validate.ps1 -VectorRuntime -PythonExecutable <absolute Python 3.13 executable> -ModelDirectory <acquired locked model> -RequestingTaskId <task UUID>`. Acquire dependencies from `VectorWorker/requirements.lock.txt` first. The command checks ownership, enforced hygiene, every model hash and installed dependency version, builds a fresh PyInstaller folder, then runs the bundled executable with only Windows on PATH. The proof denies network connections, checks 384-dimensional embeddings, writes and reopens local vector storage, and verifies search. It starts no listener. Keep `runtime-report.json`, `bundle-files.json`, `pyinstaller.log` and `isolated-proof/release-proof.json`. This component proof does not replace full all/Tier 4 validation, installer or clean-machine acceptance.

Shared portrait content lives outside program/module directories and is writable for the existing portrait tools. Installation updates must compare the last shipped file hashes and preserve locally modified portraits; uninstall must retain this content with user state.

`reign_build_release_package` assembles the setup executable and five payloads after a successful current-fingerprint `all`/`Release` report. The fallback is `reign-validate.ps1 -ReleasePackage -ValidationRunId <run> -PythonExecutable <absolute python> -BuildSpecification <absolute inputs JSON> -RequestingTaskId <task UUID>`. The local `reign-package-inputs-v1` specification supplies `downloadDirectory`, `vectorRuntimeReport`, `modelDirectory`, `portraitInventory`, `nugetDirectory`, and `innoCompiler`; it contains acquisition paths, never account credentials. Keep it outside Git. External bytes are locked in `ReignRelease/dependencies.lock.json`; vector inputs and binary hashes must match its component proof. The builder excludes private verification sources, audits the staged runtime, generates payload inventories and compiles only the checked-in Inno script. Preserve `package-report.json`, `assembly-proof.json`, `installer-compiler.log`, `package/package.json`, the setup executable and SHA256SUMS. Assembly cannot mark native or clean-computer acceptance complete.

`ReleaseInstallerTests` runs the shipped extraction/merge/removal functions under Windows PowerShell 5.1 in unique temporary directories. It proves hash rejection, archive traversal/duplicate rejection, spaces/Unicode/apostrophe paths, exact NTFS tick preservation, repair of shipped files, and preservation of edited portraits. Removal checks retain modified/unlisted files and the game root while removing an empty owned server version for reinstall. No real game module, installation record, listener or provider is touched. The first empty PostgreSQL campaign also exercises the base reputation table creation before court migration updates; existing campaigns alone cannot prove this order.

Private verification snapshots include their GUI assets and previewer contract inputs. The canonical runner supplies `REIGN_VERIFICATION_CLIENT_ASSEMBLY` from that same run's client output; release verification must not substitute an older installed binary. These private snapshots remain excluded from every runtime payload.

Use isolated installation and database directories on D: for local tests. Fresh-install proof must cover native PostgreSQL initialization, archive round trips, provider-free bundled model execution, visible server/Control Center startup, module connection, restart and repair. No second listening server may run beside the installed one. Use the supported visible lifecycle for runtime acceptance. Native campaign advancement and provider spending remain separately gated.

Initial repository/package uploads are held until the complete package has execution evidence from a clean Windows environment representing another computer, without the developer's WSL distro, Python, SDK, model cache, machine paths or credentials. Report unavailable clean-machine/native/provider coverage explicitly. The private file host remains configurable; do not embed invitation credentials in source or installer binaries.

Routine campaign discovery uses `ListCampaignMetadata`, which returns registry identity/timestamps and snapshot counts without querying relation sizes. Explicit campaign/storage reporting still uses `ListCampaigns` for actual database bytes. The isolated `pipeline.postgresql_storage` check verifies a live campaign and snapshot appear in metadata without fabricated size values. This avoids repeated filesystem metadata scans on native Windows PostgreSQL.

Windows PowerShell 5.1 preflight checks include an entirely offline package with zero missing downloads and a mixed local/download package. Do not use an empty `Measure-Object` result's `Sum` under strict mode. Visual C++ 14.50.35719.0 is the verified runtime floor for the pinned database, Codex and vector components; setup supplies 14.51.36247.0 when the existing runtime is missing or below that floor. Local source/build proof and the current-machine installer test do not establish clean-computer or native acceptance.

Atomic JSON replacement must pass `System.Management.Automation.Language.NullString.Value` as the optional backup path to `File.Replace`. Windows PowerShell 5.1 binds an untyped `$null` to an empty string, which fails when setup replaces its existing journal or installation record. Contracts cover updating an existing record, rejection while its destination is locked, preservation of the previous record and removal of the task-owned temporary file after failure.

The visible launcher must read the installation record explicitly as UTF-8. Windows PowerShell 5.1 otherwise reads a BOM-free record through the system ANSI code page and corrupts non-English paths. The contract evaluates the actual launcher's bounded record-reading expression with a UTF-8 fixture containing non-ASCII path characters; it starts no process or listener. Follow with an installed-launch check whose game and installation-record locations contain non-English characters while program and data roots meet the native database constraint below.

The pinned Windows PostgreSQL tools cannot reliably initialize a UTF-8 database from non-ASCII binary, state or password-file paths. This was reproduced with package `20260914-195057-b784fbdf` on Windows PowerShell 5.1/code page 1252 (`D:/ReignLaunch/acceptance/install-4-unicode.log`). Require ASCII program and player-data roots, allowing spaces and apostrophes. Both the folder wizard and installer preflight reject unsupported roots before payload copying; direct PostgreSQL provisioning also rejects them before running a tool. The actual installer contracts pass nonexistent game/manifest/payload inputs and prove a path-specific rejection with no created program directory, data directory or record. Keep Unicode game, content filenames, payload and installation-record support. A Unicode-only Windows home may require a separately writable ASCII destination; do not claim unrestricted path support or change system locale. See the [PostgreSQL explanation](https://www.postgresql.org/message-id/642665.1738684548%40sss.pgh.pa.us).
