## Campaign storage retirement

Use `reign_get_campaign_storage_audit` before and after campaign cleanup. It inventories the physical Bannerlord `.sav` directory and separates matching saves from missing or overwritten Save Sync registrations, durable pending final-save retirements, physical zero-save campaigns, imported campaigns awaiting first load, orphan campaign/Save Sync/portrait roots, and the protected `_shared` portrait library. Stored Reign snapshots are not evidence that the corresponding native save still exists. A zero-save campaign must be shown as having no matching physical Bannerlord save and eligible for permanent deletion unless it is an import awaiting first load; an unavailable save directory must preserve every campaign.

Bulk cleanup is available only through `reign_cleanup_campaigns_without_saves` with the exact confirmation `delete Reign campaigns with no saves` and with Bannerlord stopped. The server re-audits immediately, deletes campaigns with no physical save, prunes stale registrations from retained campaigns, removes verified orphan campaign/Save Sync/portrait roots, preserves imported campaigns awaiting first load and `_shared`, stages campaign data only through verified direct-child roots outside `PortraitCache`, and returns reconciliation counts, per-subsystem deletion counts, and retryable residual paths. The persistence boundary test is `ReignBetaServer --run-save-sync-tests --json`; it covers physical-save ownership, reused-slot retirement, unavailable-inventory fail-safe behavior, multi/final-save deletion, active deferral, unload/startup recovery, database-only retirement without recreation, cancellation, unmatched events, protected imports, idempotency, traversal/shared-root rejection, orphan cleanup, interrupted writes, and partial cleanup reconciliation.

**Export Complete Backup** produces a portable version-3 diagnostic bundle: every physical `.sav` owned by the selected campaign is included alongside its database, campaign files, Save Sync generations, and portrait cache. Import validates the archive manifest and hashes before restoring those native saves to Bannerlord's save directory. A different existing `.sav` with the same filename blocks import unless the operator separately enables native-save replacement; replacing the Reign campaign alone never implies native-save overwrite. Version-2 archives stay readable but remain non-portable and are marked as awaiting their externally supplied native save. The campaign-backup and Save Sync self-tests prove exact native byte round-trip, conflict rejection, explicit replacement, manifest inventory, and legacy compatibility.

## Visible lifetime rules

- The supported server is `http://127.0.0.1:5101`.
- Start it only through the visible unified launcher or `Start ReignBeta Server.cmd`.
- Never start a hidden or second server and never open the Control Center in an ordinary browser tab.
- Treat the server console, dedicated Control Center, and vector worker as one lifetime group.
- Use the packaged `ReignLiveTest.exe` or guarded MCP lifecycle tools for Bannerlord. Re-observe status before every start or restart.

## Autonomous campaign sequence

1. Call `reign_prepare_campaign_test` with the exact campaign, timeline, baseline save, run ID, and descriptive test objective.
2. Call `reign_start_campaign_test`. It attaches when the correct save is already loaded or visibly starts Bannerlord on the enrolled baseline/current checkpoint.
3. Call `reign_arm_campaign_test`. The harness verifies the native active save, campaign, timeline, Save Sync, and settlement safety, then creates the task-named disposable `Current` copy before allowing time advancement. Only this initial baseline-copy step may accept an absent pre-existing daily rollup, and only after exact native observation and confirmation at the target day; pending queues and current subsystem failures still block, and ordinary or post-advance checkpoints receive no exception.
4. Capture `reign_get_campaign_test_status` and the relevant subsystem overviews as the baseline.
5. Call `reign_advance_campaign_test` with exactly one of `days` or `targetDay` and an explicit checkpoint mode. Prefer `none` until an acceptance boundary is healthy. Guarded advancement closes only an already-open native MapScreen Escape menu before and during settlement waiting, records `escapeMenuRecoveryCount`, and never uses synthetic input or dismisses another screen or inquiry through that recovery. The native heartbeat publishes the exact executing `world_advance` run as `activeMode=passive_world`. If its controller process times out or the MCP request is cancelled, MCP terminates only that child controller, cancels the exact advertised native run, waits for native execution to become idle, and attempts a cancellation-independent queue drain. This recovery never saves; an unproven cancellation or drain remains a failed boundary.
6. At a boundary, call `reign_stop_campaign_test`. It first preempts an exact active passive-world run, then pauses time, acknowledges ordinary notices, drains pending work, and requires a stable quiescence window. It refuses to cancel a busy non-passive feature run. Daily clocks must cover the latest fully completed campaign day; a paused fractional current day is not itself a completed daily cycle.
7. Inspect relationships, diplomacy, political pressure, clan conflicts, rumors, rebellions, actions, Save Sync, storage, memory, and affected feature telemetry.
8. Call `reign_checkpoint_campaign_test` only after the quiescence gate passes. Default to overwriting the one rolling checkpoint; retain a milestone only when the 15-state budget permits it.
9. When a test requires a real load boundary, call `reign_restart_campaign_test` immediately after that checkpoint. It refuses any uncheckpointed or non-owned save, visibly restarts Bannerlord on the exact run-owned `Current` save, and returns a durable reload receipt. If a native fixture instead leaves unsafe unsaved encounter/menu state, use `reign_restore_campaign_test_checkpoint`: its pre-reload gate proves the enrolled campaign, timeline, exact owned active save, and finalized Save Sync without requiring the transient state itself to be in a safe settlement; it never saves that state, requires an existing exact owned Current checkpoint distinct from the baseline, visibly reloads it with `--no-save`, and requires the restored snapshot to be safe. Its restore receipt is recovery evidence and cannot satisfy a feature save-roundtrip case.
10. Resume with the same run ID. Never create a new run merely because Codex, Bannerlord, or Reign restarted.
11. Produce `reign_get_campaign_test_report`. Cleanup is explicit and may delete only exact run-owned saves while the baseline remains protected.

## Save and queue safety

- A baseline is immutable even when its filename looks disposable.
- The harness must observe the actual `MBSaveLoad.ActiveSaveSlotName`; controller memory or a “last save” text file is not authoritative.
- Do not save while diplomacy, world-history upload, native relationship sync, political pressure, clan conflict, Save Sync alignment, or another native save is active.
- Any failed queue item blocks checkpointing and requires diagnosis.
- `pipeline.failedActions` must be present and zero before saving and in the final checkpoint status. A positive or missing count returns `action_health_failed`; compact evidence includes `failedActions`. A lawful government `decided/reject` result is terminal `rejected`, consumes no execution retry, and applies no agreement/payment effects. On load, only an exact unchanged government business with that recorded rejection can repair the old `government_refused` misclassification; ordinary failures and changed terms remain blocked. Architecture regressions verify action/announcement correction and replay, while MCP tests exercise missing and positive failure telemetry.
- Diplomacy announcement quiescence counts only `announcementReady=true` events, matching the native delivery API. A government decision awaiting its lawful deadline remains a pending action, not an announcement to acknowledge while time is paused. Once execution marks the announcement ready, delivery and acknowledgement must drain before saving. World Test regressions cover this transition alongside delivered, acknowledged, and missing-readiness cases.
- Save Sync retains at most 15 unique states. Use one rolling checkpoint by default. Never delete a baseline to make room.
- `world-test status`, `drain`, `checkpoint`, and `advance` return bounded receipts so long campaign runs cannot lose a successful status or save to controller-output truncation. `status` uses the compact runtime/checkpoint view; inspect the full World Test overview through its dedicated API/MCP route. A checkpoint or rolling-advance receipt projects `saveName`, `worldDay`, native-save completion, and Save Sync finalization from the completed nested save command, then waits up to 45 seconds for five stable seconds of matching current post-save runtime telemetry. Save Sync must be aligned and ready; diplomacy, the native relationship daily-input outbox, World History, and native saving must all be idle; finalization must name the requested save. Empty placeholder fields, a stale busy/in-flight heartbeat, or a late final-day relationship capture are never acceptable proof. Use the receipt's `reportPath` or the normal live-test report APIs for full command evidence.
- World Test treats an action status of `rejected` as a resolved outcome, including a lawful NPC-government veto. Only actual terminal failures (`failed`, `blocked`, `expired`, or `validation_failed`) make diplomacy/pipeline health fail.
- Passive-world advancement acknowledges one tracked Reign kingdom-event inquiry at a time before reasserting native settlement wait. Stacked event announcements remain individually correlated and cannot leave an empty modal layer blocking campaign time. Use this guarded disposable-campaign seam only after observing or producing the expected ordinary announcement context.
