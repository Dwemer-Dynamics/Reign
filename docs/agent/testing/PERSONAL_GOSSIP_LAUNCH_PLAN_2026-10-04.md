# Personal NPC gossip: autonomous launch acceptance

Status: proposed for user acceptance on 2026-10-04. Execution and goal creation begin after acceptance. This document is an execution contract, not a claim that native testing has passed.

## Objective and completion condition

Certify personal NPC gossip on the final installed client/server and configured dialogue providers by playing through production conversations, travel, waiting, saves and reloads. Exercise positive sharing/consultation, deliberate negative gossip including fabrication, and good/bad impressions. Find and fix implementation or integration defects, validate and deploy the fixes, and continue until the required evidence passes.

After acceptance, create one Codex goal with this objective:

> Make personal NPC gossip ready for launch on a verified disposable Bannerlord campaign: implement any missing guarded test capabilities, execute this plan's complete case/variant manifest through production dialogue and native time, repair and validate/deploy failures, and finish only with a clean final-candidate certification report, verified persistence and isolation, restored settings, and retained replay evidence.

The goal has no inferred token budget. It continues across ordinary interruptions, game/server restarts and Codex restarts under [continuity procedures](../CONTINUITY.md). A successful API command, old offline pass, or entertaining gossip example cannot complete it. This is certification of this feature on the recorded configurations; it does not certify every other Reign feature or authorize publishing a release.

## Phase 3: deterministic coverage without artificial passes

Use three explicit evidence strata:

| Stratum | Control | What it proves |
|---|---|---|
| Controlled native mechanics | Fixed prerequisites, exact stage rolls, captured/injected composer outputs and scoped faults | Native audience/timing/storage/persistence and rare branch behavior |
| Real-provider natural dialogue | Same controlled prerequisites/rolls when needed; real production writer, extraction, gossip composition and reply | Model interpretation and wording through actual player conversations |
| Default play | Shipping settings and original production draws; no roll overrides or injected output | Ordinary frequency, silence, variation and integration during play |

Never count injected output as model quality or controlled rolls as measured default frequency. A declined saved roll is a correct default outcome if the independent oracle predicts it. A missing valid signal in a real-provider case requiring one is an extraction failure, not a reason to inject metadata. Preserve the original miss.

Boundary rolls use the documented inclusive d100 comparison: test success at the calculated percentage and rejection at percentage+1, plus 0% and 100% endpoints. For weighted selection, compare the cumulative intervals independently from the user formulas and sweep fixed draws; do not copy the production selection helper as the oracle. The 80% examples are conditional on reaching selection. Use a fixed 10,000-point draw grid for exact/rounding coverage, with at most one-grid-bin error for repeating fractions. These sweeps are provider-free and do not require thousands of game conversations.

Trait checks include excitable, reserved/discreet, honest/loyal, and dishonest/vengeful profiles; exact boundaries and all low/high extremes remain in the offline oracle. Compare resulting probabilities, not whether a low-probability NPC happened to speak. For example, emotion 75 with sociability 90, impulsiveness 70, pride 60 and curiosity 85 yields sharing 63%; emotion 75 with 15/10/30/35 yields 25%. Privacy classification and feelings still require accepted source evidence.

## Phase 5: natural conversations and varied playstyles

Run **96 base real-provider cases**: eight story families × six playstyles × normal/High Memory. If preflight discovers another supported user-selectable memory mode, expand its relevant cases rather than claiming coverage from these two. Each base case owns its required subepisodes and variants; multiple episodes never share a rerolled topic.

| Playstyle | How the simulated player behaves |
|---|---|
| Warm/social | Speaks openly, shares an enjoyable event, follows friendly questions. |
| Reserved/private | Gives little detail, sets a confidence boundary, answers briefly. |
| Curious/family diplomat | Asks about another NPC politely and answers actual family concerns. |
| Flirtatious/romantic | Uses appropriate adult actors, private affection and indirect implications. |
| Provocative/rivalrous | Discusses a real rivalry or injury; distinguish provocation from a quoted insult. |
| Practical/roaming | Short task-oriented conversation, abrupt departure, travel, waiting and quick revisits. |

| Story | Production interaction and expected distinction |
|---|---|
| N1 Ira/Rhagaea local | First have a fresh actual conversation with Rhagaea. Tell Ira naturally, e.g. “Your mother spoke with me earlier. I wondered whether she mentioned why.” Ira may ask Rhagaea; no private content is forwarded automatically. Verify family relationship and the mother's own accessible evidence. |
| N2 Ira/Rhagaea remote | Repeat with Rhagaea genuinely elsewhere. Visit before outbound delivery and speak to Ira before the return. Neither may report the future message/answer. After delivery, allow a grounded answer, refusal or evasion. |
| N3 excited sharing | Discuss a distinctive, harmless enjoyable experience with an eligible sociable NPC. A local friend hears the supported experience; an unnamed distant friend cannot. |
| N4 confidences | Entrust a clearly classified personal/secret detail and, separately, an explicit promise. A discreet NPC with a failed disclosure roll reveals no detail; a policy-permitted betrayal remains an attributed act. Test family as well as friendship. |
| N5 malicious account | Have a real private conversation with a dishonest, vengeful NPC who has an evidence-backed rival. Exercise the permitted false overnight claim. Source memory remains the private conversation; the rival hears a claim and the author remembers the distortion. Truthful and low-motive controls are required. |
| N6 impressions | Two distinct subepisodes: a positive encounter and a bad experience with the player. Eligible friends/family hear only that it went well/badly. The bad impression does not require disliking the listener. Include a zero-net-change conversation. |
| N7 ambiguous speech | Use reported insults, hypothetical meetings, negation, corrections, similar names and innocuous mentions. Do not turn “we did not spend the night together” into intimacy or hostility. New corrected speech must not rewrite historical truth. |
| N8 uncertain report | Hear a claim with weak/contradictory evidence, later receive an independent correction, and revisit it after retelling and reload. Maintain speaker attribution, belief uncertainty and the difference between reported and witnessed events. |

Every case uses fresh source events and stable harmless markers so old conversations cannot accidentally satisfy the oracle. Do not replay or revise the player's historical Ira/Rhagaea exchanges. Permit at most two genuine contextual follow-up turns, selected from the immediately preceding reply, plus source/setup and before/after recipient probes. A legal refusal is recorded honestly; it does not become consent or a successful intended branch.

The player never says “output gossipSignals,” supplies stage rolls, names a hidden recipient feeling, or reads operator job state into speech. The driver may select and observe actors through the harness, but conversational inputs and production consequences remain normal. Roleplay pauses, interrupted conversations and busy/no-response handling are part of the matrix.

Use neutral recipient probes before arrival (“Good afternoon. How has your day been?”), not leading questions that reveal the source fact. Separate sender and recipient perspectives. Player behavior cannot establish private NPC knowledge just by guessing a rumor. Some cases must allow spontaneous discussion after delivery; others ask explicitly. Correct silence under a failed raise roll is not a failure.

Real-provider cases may control an otherwise permitted branch to avoid waiting for chance; they must retain real extraction and wording. Also run three default-setting journeys—sociable court visitor, private family/romance player, and mobile pragmatic player—without roll overrides. At least 12 substantive conversations per journey, with prescribed ordinary activities and valid no-gossip controls, are recorded. Inspect every accepted topic's predicted versus actual outcome rather than requiring a lucky number of gossip messages.

Provider latency is reported separately and does not excuse blocked UI or duplicate effects. Reassess a numerical gate only with evidence and a recorded design decision, never to hide a failure.

## Autonomous execution and repair loop

Execution order: preparation → missing harness/contracts → validated deployment → deterministic native cases → real-provider/playstyle matrix → native input → persistence/faults → default journeys/soaks/performance → final-candidate regressions → restore/cleanup → readiness report.

Checkpoint the durable case ledger and Project Memory after every material milestone and before any restart. A checkpoint names completed IDs, failures, exact fingerprints/evidence, current runtime/save state, used/remaining provider budget and next action. Goal continuation resumes the same run and skips compatible completed cases; it does not reset the campaign or rerun passed work merely because the chat restarted.

For a failure: pause native time, retain the smallest complete reproduction, distinguish harness/infrastructure failure from product/model failure, repair the responsible code or capability, obtain its exact-path validation plan, run canonical checks, deploy validated artifacts under managed lifecycle, invalidate affected certificates, and rerun the failing case plus dependent controls. A revised fixture, prompt or oracle must retain the old failure and explain the corrected requirement. Do not force a passing response or relax an acceptance assertion to finish.

Ordinary popups, focus loss, transport errors and managed restarts are recovery work. Re-observe state, then use supported MCP, harness, native UI, logs or documented fallback. Close only exact run-owned transient UI and cancel only the exact native run. Do not advance or save until recovery/quiescence is proven. After a required Codex restart, use the prescribed restart-and-resume capability and reload the durable checkpoint.

Continue until the goal's completion condition is met, the user explicitly pauses/cancels, or a genuine external/authority blocker persists for the required three consecutive goal turns after supported recovery. Budget exhaustion is a real authority boundary. An inconclusive test remains incomplete; it never becomes a pass because time ran out. Stop game/server only through managed supported routes, retain baseline and replay evidence, and restore the final user state even when an execution failure requires handoff.

The final report gives ready/not-ready, tested configurations, all required pass/quality counts, provider usage, performance results, exact validation/deployment fingerprints and hashes, saved-state isolation/restoration, and remaining limits. Set the Codex goal complete only after that report's verifiable ready condition is achieved.
